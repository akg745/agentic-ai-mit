Rise of the Horizontal Architecture in the Agentic Era

A layer-by-layer guide to the technical architecture behind replatforming — pre-class reading and layer sort exercise

Introduction

Organizations are shifting from vertical ownership, where each business division builds and owns its own closed technology stack, to a horizontal architecture, where a shared set of layers sits underneath every division and is accessible to any application, human, or AI agent that needs it. Replatforming is the process of moving a legacy system from the old vertical world to the new horizontal one.

Why replatform?

Vertical architecture is not an entirely wrong choice, it is just expensive to keep and harder to drive ROI from in an agentic world. When each division builds its own closed stack, its own interface, its own integration logic and its own systems and source of data, that duplication stays invisible as long as nothing needs to cross divisional lines. However, this issue stops being invisible the moment an AI agent has to reason across more than one division's data or logic in a single task, or two divisions independently build the same integration against the same vendor system.

Replatforming does not throw away what each division already has; it takes the pieces that keep getting rebuilt behind every division's closed stack like orchestration logic, capability APIs, model access, data access and rebuilds each one once as a shared layer that any division or agent can call, instead of many times behind many closed doors. This enhanced accessibility makes agentic tools more efficient and improves their ROI and effectiveness across the organization.

A concrete version of this in pharma. Before replatforming, a Commercial team might maintain its own custom integration to pull product and safety data for field sales dashboards (e.g., knowing a product's current safety profile before a rep discusses it), while Regulatory Affairs maintains an entirely separate, custom-built pipeline to pull much of the same underlying data for tracking drug approval submissions to regulatory authorities. Both integrations talk to overlapping databases and systems but neither can be reused by the other, because each was built as part of a closed, division-specific stack rather than as a shared layer. That is what a vertical architecture looks like in practice, and it is exactly the duplication that replatforming helps to remove.

Horizontal, AI-native architecture

Each arrow points from a layer to the layer or system it calls or relies on.

A layer belongs in the shared stack only if two different divisions, or two different agents, could call the exact same instance of it without modification. Certain Systems of Record can fail that test today, which is why they need to be wrapped by Capability Services rather than left as the thing agents call directly.

Layer reference

An explanation of each layer from top to bottom, in the same way a user would encounter the stack: starting from the interface they touch, down through orchestration and shared capabilities, to the infrastructure everything runs on.

User Experience
What it does. The conversational and workflow surfaces a human uses to reach everything beneath. This is the head in "headless"; the part that stays division-specific by design.
Why it matters for agents. This is where a human's request becomes a task and where the agent's output comes back. It starts the job, providing vital data for the agent to decide which layers (models, databases and tools) to use.
Examples. PharmaCo's internal assistant and Microsoft Copilot, agentic coding tools like Claude, Cursor, and Codex.
Agent Orchestration
What it does. Layer with various agents and tools that call whatever agents need across the Model Plane, Capability Services, and Data Plane, often more than one in a single task. This layer is not one rung in a pipeline; it is a hub with edges into multiple layers at once.
Why it matters for agents. This is the reasoning and coordination layer itself. It decides what to call, in what order, and stitches the results together, so a task needing both a capability call and a model call is executed as one coherent step.
Examples. An agent validating a regulatory submission pulls model reasoning, calls a capability API for safety-signal data, and queries the data fabric for manufacturing records.
Capability Services
What it does. The layer this case is actually about: thin, standardized APIs (Application Programming Interfaces; the standard way two pieces of software talk to each other). This layer can expose data, business and validation logic across divisions.
Why it matters for agents. This is what lets an agent call a business function reliably, without hardcoding vendor-specific logic for each system. Without it, every agent that needs (for example) a "regulatory status" has to know which vendor holds it.
Examples. Not yet built at scale at PharmaCo; this is the layer Systalyze's pilot is standing up in front of PharmaCo's existing systems of record. More broadly, the internal API layers companies build to extract data from, or connect with, vendor platforms.
Model Plane
("AI Platforms")
What it does. Model hosting, fine-tuning, and embeddings, abstracted so the orchestration layer above does not need to care which vendor or model sits underneath.
Why it matters for agents. This is what the agent reasons and generates with. Abstracting it means a model can be upgraded or swapped without rewriting how orchestration calls it.
Examples. PharmaCo's own gen-AI gateway alongside Azure AI Foundry, AWS Bedrock, and Google Vertex AI.
Data Plane
What it does. Unified, governed access to data that otherwise used to be locked inside each division's own systems. A peer to the Model Plane, not a step before or after it; both sit directly on Infrastructure.
Why it matters for agents. This gives an agent one governed place to pull data from across divisions, which is what makes cross-division reasoning possible instead of requiring bespoke access to each division's silo.
Examples. Databricks, Snowflake, and Google BigQuery give every division, and every agent, a common place to find data rather than a private knowledge silo.
Infrastructure
What it does. Raw compute, storage, and networking. Nothing AI-specific or business-specific happens here; everything above is built on top of it.
Why it matters for agents. Agents need well-instrumented infrastructure to be reliably provisioned underneath everything else they touch.
Examples. PharmaCo runs across Microsoft Azure, Amazon Web Services, and Google Cloud.
Systems of Record
(outside the stack)
What it is. Vendor SaaS owned division by division: Workday, SAP, Salesforce, Veeva, ServiceNow. Runs on its own vendor infrastructure, not PharmaCo's, which is part of why it sits outside the shared stack.
How it connects. Capability Services wrap it, and the Data Plane ingests from it (batch). Agents call the wrapper, not the vendor system directly.
